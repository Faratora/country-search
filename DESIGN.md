# Design Document

## 1. Отмена устаревших запросов

### Почему не хватает флага «актуальный ответ»

Наивный подход — хранить в состоянии флаг «этот ответ самый свежий» и
игнорировать устаревшие ответы в колбэке. Проблема в том, что `fetch`
работает асинхронно и **нет способа отменить уже запущенный запрос, не
используя `AbortController`**. Если запрос отправлен, сервер всё равно
обрабатывает его и в итоге возвращает ответ. Флаг лишь «отфильтрует»
ответ на клиенте, но:

- сетевые ресурсы (TCP-соединение, буферы) не освобождаются;
- на медленных сетях (3G, throttling) устаревший ответ может прилететь
  и рендернуться, если флаг проверен с опозданием;
- код становится запутанным — нужно сравнивать таймстампы или номера
  запросов при каждом резолве.

### AbortController — реальная отмена

В `SearchController.updateQuery()` метод `abort()` вызывается **синхронно**
при каждом изменении ввода — ещё до того, как debounce сработает и
отправит запрос. Это означает:

1. Если предыдущий запрос уже в полёте — `AbortController.abort()`
   немедленно отменяет `fetch`, освобождая сетевые ресурсы.
2. Если предыдущий запрос ещё не отправлен (debounce не сработал) —
   `abort()` всё равно вызывается, что предотвращает отправку
   устаревшего запроса.

### Различение AbortError / TimeoutError

В блоке `catch` ошибки обрабатываются строго по категориям:

| Тип ошибки                         | Происхождение                        | Действие                            |
| ---------------------------------- | ------------------------------------ | ----------------------------------- |
| `DOMException AbortError`          | Пользователь ввёл новый символ       | Игнорировать (не ошибка)            |
| `DOMException TimeoutError`        | `AbortSignal.timeout(8000)` сработал | Показать ошибку + кнопку «Повторить» |
| `HttpError` (статус 500 и выше)    | `response.ok === false`, статус ≠ 404 | Показать ошибку + кнопку «Повторить» |
| `404 Not Found`                    | `response.status === 404`            | Вернуть `[]` — «ничего не найдено»   |
| Прочие `Error` (network)           | Нет сети, DNS-ошибка и т.д.          | Показать сообщение об ошибке         |

`AbortError` от `AbortSignal.timeout()` и от `AbortController.abort()` —
это **один и тот же тип** `DOMException` с `name === 'AbortError'`, но
в `SearchController` таймаут комбинируется с контроллером через
`AbortSignal.any()`, и когда таймаут срабатывает первым — он выбрасывает
`TimeoutError`, а не `AbortError`. Это позволяет различить их.

> **Примечание:** `AbortSignal.timeout()` выбрасывает `DOMException` с
> `name === 'TimeoutError'` при срабатывании. `AbortController.abort()` —
> `DOMException` с `name === 'AbortError'`. Комбинация через
> `AbortSignal.any()` гарантирует, что таймаут не перепутается с
> пользовательской отменой.

### Скомпонованный сигнал

```typescript
const controller = new AbortController();
this.controller = controller;

const { signal: combinedSignal, dispose } = combineSignalsWithTimeout(
  controller.signal,
  REQUEST_TIMEOUT_MS,
);
```

Это позволяет одновременно:

- отменять запрос при каждом новом вводе пользователя;
- отменять запрос при истечении 8 секунд ожидания.

В современных движках `combineSignalsWithTimeout` делегирует
`AbortSignal.any([cancelSignal, AbortSignal.timeout(ms)])`. Если
`AbortSignal.any` недоступен, оба источника компонуются вручную:
собственный `AbortController`, который abort'ится либо по сигналу
пользователя (с его `reason`), либо по `setTimeout` с
`DOMException('TimeoutError')`. Таким образом таймаут работает на
любом движке. `dispose()` в `finally` снимает слушатели и сбрасывает
таймер.

## 2. Debounce

### Выбранная задержка: 300 мс

| Задержка    | Поведение                                                   |
| ----------- | ---------------------------------------------------------- |
| 0 (нет)     | Запрос на каждую букву — десятки запросов за 2 секунды     |
| 100 мс      | Слишком быстро — запросы всё ещё «дребезжат»               |
| **300 мс**  | **Баланс: пользователь не ждёт, запросы не дребезжат**     |
| 500+ мс     | Задержка ввода ощутима — пользователь ждёт результата      |
| 1000+ мс    | Приложение «тормозит» — ощущение оторванности от ввода      |

300 мс — это де-факто стандарт для поиска:

- пользователь успевает видеть результаты сразу после набора слова
  (~5 слов в минуту → ~100 мс на букву, 300 мс даёт буфер на 3 буквы);
- запросы не отправляются на «пустышки» вроде «s», «sp», «spa»;
- при быстром наборе отправляется не больше 1–2 запросов вместо 10–20.

### Что будет без debounce

Для слова «javascript» (10 букв):

- Без debounce: 10 запросов к API
- С debounce 300 мс: 1 запрос к API
- Экономия: 9 запросов (90%)

### Что будет при слишком большой задержке

При задержке 1000 мс пользователь вводит слово за ~1 секунду — результат
придёт только через секунду после завершения ввода. Это ощутимая задержка,
особенно на быстрых соединениях.

## 3. Сложность (Big O)

### mapCountryResponse — O(n)

Функция `src/api/mapCountryResponse.ts`:

- Копирование скалярных полей: O(1)
- `languages`: массив объектов, `Array.map` — O(n), где n = кол-во языков
  (обычно 1–3, максимум ~10)
- `currencies`: аналогично O(n), где n = кол-во валют (обычно 1)
- `area`, `borders`, `description`: O(1)

**Итог:** O(n), где n — количество языков/валют в ответе. В среднем
постоянная величина ≤ 10, поэтому на практике O(1).

### Кэш и дедупликация — O(1)

Реализованы в `src/utils/cache.ts`, интегрированы в `SearchController`.

**Кэш результатов по строке запроса** — `Map<string, CachedResult>`,
синхронизированный с `localStorage` (ключ `country-search-cache`, TTL
5 минут, максимум 100 записей):

- `getCached(query)`: O(1) — хэш-поиск по ключу;
- `setCached(query, raw)`: O(1) — добавление в Map;
- очистка протухших записей: O(n) при загрузке, n = размер кэша.

При попадании в кэш `updateQuery()` показывает результат мгновенно,
не дожидаясь debounce и не обращаясь к API.

**Дедупликация одинаковых запросов «в полёте»** —
`Map<string, Promise<unknown[]>>`:

- `getCachedOrInflight(query)`: O(1);
- если промис уже в карте, новый вызов ждёт существующий промис
  вместо создания нового `AbortController` и нового `fetch`.

**История поиска** — последние 10 уникальных запросов в `localStorage`
(ключ `country-search-history`, newest-first, регистронезависимая
дедупликация):

- `addToHistory(query)`: O(n) из-за линейного поиска дубликата, n ≤ 10 —
  фактически O(1);
- рендерится в UI как чипы-кнопки («Recent searches»); клик по чипу
  подставляет запрос в поле и запускает поиск (обычно из кэша — без сети);
- `clearHistory()` — кнопка «Clear history».

Все операции с `localStorage` обёрнуты в `try/catch`: переполнение
хранилища или его недоступность (приватный режим браузера) не ломают
поиск — приложения деградирует до работы без кэша и истории.

## 4. Принципы чистого кода

### 4.1. Чистые функции

| Функция                   | Где         | Почему чисто                                |
| ------------------------- | ----------- | ------------------------------------------- |
| `mapCountryResponse`      | `src/api/`  | Нет побочных эффектов, нет сети, нет DOM    |
| `debounce`                | `src/utils/`| Задержка и сброс — чистая логика таймеров   |

Чистая `mapCountryResponse` означает, что:

- она легко тестируется на заготовленных JSON-данных без сети;
- её можно рефакторить без страха сломать сетевую логику;
- она не знает о `fetch`, DOM, состояниях приложения.

### 4.2. Разделение ответственности

| Модуль                     | Отвечает за                                    |
| -------------------------- | --------------------------------------------- |
| `debounce`                 | Задержка вызовов + отмена отложенного вызова   |
| `cache`                    | Кэш результатов, дедупликация, история (localStorage) |
| `searchCountries`          | HTTP-запрос + разбор статусов                  |
| `HttpError`                | Типизация HTTP-ошибок                          |
| `mapCountryResponse`       | Преобразование сырых данных API в UI-формат    |
| `SearchController`         | Состояние, отмена, таймаут, обработка ошибок   |
| `ui.ts`                    | Рендеринг в DOM                                |

`searchCountries` **не создаёт** `AbortController` — он принимает `signal`
снаружи. Это позволяет:

- мокировать `fetch` в тестах без реальных запросов;
- передавать любой сигнал (таймаут, отмена, комбинация);
- тестировать `searchCountries` независимо от UI.

### 4.3. Single Responsibility Principle

`SearchController` инкапсулирует всё, связанное с управлением поиском:

- debounce-обёртку вокруг `executeSearch`;
- `AbortController` для отмены предыдущего запроса;
- комбинацию сигналов (`AbortSignal.any`) для таймаута;
- обработку всех типов ошибок (AbortError, TimeoutError, HttpError,
  network error);
- публичный интерфейс `updateQuery()` и `retry()`.

UI (`ui.ts`) **не знает** о `fetch`, `AbortController` или типах ошибок —
он только подписывается на изменения состояния через `onStateChange` и
рендерит `SearchState`.

### 4.4. No innerHTML

Весь динамический контент создаётся через `document.createElement` +
`textContent` — безопасный способ вставки текста, который не может быть
интерпретирован как HTML. Это защищает от XSS: даже если сервер вернёт
`<script>alert(1)</script>` в поле `name`, оно будет отображено как
текст, а не выполнено.
